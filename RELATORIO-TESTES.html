Autenticação 28 passando src/modules/auth/auth.service.spec.ts

  • guarda a senha com hash bcrypt, nunca em texto puro
  • a resposta do registro não devolve o hash da senha
  • senha errada e e-mail inexistente dão a MESMA mensagem
OTP do cliente por WhatsApp
  • não sobrescreve o nome de uma conta existente
  • usa o nome apenas ao criar conta nova
  • o código enviado tem 6 dígitos
  • aceita o código correto e limpa o OTP
  • conta a tentativa quando o código está errado
  • invalida o código ao estourar o limite de tentativas
  • código expirado é recusado e apagado
  • conta inexistente, código errado e expirado dão a MESMA mensagem
OTP do dono — enumeração de conta
  • responde igual exista ou não a conta
  • não envia OTP quando a conta não existe
  • falha no envio não vira sinal de existência de conta
  • limite de tentativas também vale para o dono

  • a confirmação busca pelo hash do token recebido
  • token inválido é rejeitado

Fidelidade 15 passando src/modules/loyalty/loyalty.service.spec.ts
Dois bugs econômicos: marcar concluído+pago e cancelar em seguida mantinha o ponto (fidelidade acumulável sem atendimento), e o resgate gravava o saldo calculado em memória — dois resgates simultâneos entregavam dois prêmios com um débito só.
Concessão
  • credita 1 ponto em atendimento concluído e pago
  • não credita se o atendimento não foi concluído
  • não credita se o pagamento está pendente
  • é idempotente: chamar duas vezes credita uma vez só
  • perdedor da corrida não credita (updateMany count=0)
  • ignora agendamento inexistente sem estourar
Reversão
  • devolve o ponto quando o atendimento deixa de ser concluído
  • nunca deixa o saldo ficar negativo
  • não reverte duas vezes
Resgate e status
  • recusa abaixo da meta
  • debita exatamente a meta de forma atômica
  • resgate simultâneo: só um passa
  • rejeita cliente inexistente
  • calcula quanto falta para a recompensa
  • nunca reporta restante negativo com saldo acima da meta
Geração de OTP e tokens 13 passando src/common/security/otp.util.spec.ts
Math.random() é um PRNG não criptográfico e previsível a partir de algumas saídas observadas — um atacante poderia derivar o próximo OTP de outra pessoa.
  • gera sempre o número correto de dígitos (500 amostras)
  • preserva zeros à esquerda (000042 não vira 42) — recupera 10% do espaço de busca
  • não repete de forma detectável em amostra grande (2000 amostras)
  • aceita valores iguais / rejeita valores diferentes
  • rejeita nulo, indefinido e vazio dos dois lados
  • rejeita valores de tamanhos diferentes sem estourar
  • gera token longo e imprevisível (32 bytes)
  • o hash guardado difere do token enviado
  • hash é determinístico — permite buscar pelo token recebido
  • tokens sucessivos são distintos (200 amostras)
  • expira no TTL configurado · sempre no futuro
Validação de ambiente 10 passando src/config/env.validation.spec.ts
A API subia sem JWT_SECRET e com CORS travado em localhost. Agora ela falha rápido na subida em vez de rodar insegura em produção.
  • aceita uma configuração mínima válida
  • exige DATABASE_URL · exige JWT_SECRET
  • recusa o segredo de exemplo do .env.example
  • exige segredo longo em produção (≥32 caracteres)
  • exige CORS_ORIGINS explícita em produção
  • não deixa produção herdar localhost no CORS
  • em desenvolvimento o CORS cai no padrão local
  • recusa PORT inválida (0, texto, >65535)
  • acumula todos os erros numa mensagem só

A suíte cobre 3 viewports (celular, tablet, desktop) no mesmo comando: ausência de scroll horizontal, elemento vazando da janela, controle escondido por media query, alvo de toque pequeno demais, e os contratos de API — incluindo o 429 do rate limit e a ausência de stack trace na resposta de erro. Rode com npx playwright install && npm run test:e2e.

Checagem de tipos do backend — npm run typecheck

O CDN de engines do Prisma também está bloqueado, então prisma generate não rodou e o tsc --noEmit não foi executado até o fim. Os testes usam SWC e rodam sem isso, mas a checagem de tipos precisa ser rodada na sua máquina antes de confiar no build.

A aplicação NestJS nunca subiu

O schema e as constraints foram validados contra um PostgreSQL 17 real, mas os endpoints HTTP não foram exercitados de ponta a ponta. Guards globais, helmet e rate limit estão cobertos por teste estrutural e unitário, não por requisição real.
